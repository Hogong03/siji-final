# 后台保活方案（4.35.0）

> 一句话：Android 上做**前台服务 + 常驻通知**，让思迹退后台、从最近任务划掉后进程尽量不被回收；
> iOS / H5 / 小程序无对应能力，本方案只在 Android 生效，其余端全部静默降级。

---

## 1. 它能做到什么，做不到什么

| 场景 | 4.35.0 之前 | 4.35.0 之后 |
|---|---|---|
| 退到后台（进程还在） | 60s 轮询继续，到点 toast + 通知 | 同左，但**进程不容易被系统回收**（前台服务优先级） |
| 从最近任务划掉 | JS 全死，只能靠 4.22.0 本地推送到点弹通知 | 服务 `stopWithTask=false` + `START_STICKY`，进程大概率存活、轮询继续；被杀也仍有本地推送 |
| 划掉后 7 天没打开 App | 推送窗口滚不动，提醒断 | 同左（**这条没解决**，要解只能上服务端定时任务） |
| iOS | 无 | **无**（iOS 不允许，只能 APNs 远程推送，需要服务端） |
| H5 / 微信小程序 | 无 | **无**（浏览器/小程序没有常驻概念） |

**明确的边界**：

- 前台服务提高存活率，但**不保证**国产 ROM（MIUI / EMUI / ColorOS）在「电池优化未豁免 / 自启动关闭」时不杀。用户侧设置只能引导，不能替用户改。
- 服务本身**不持 wake lock**，不跑循环，只维持前台状态 —— 耗电影响接近 0（代价是通知栏常驻一条）。
- 常驻通知是用户可见的副作用，所以开关**默认关**，必须用户自己打开（设置 → 提示与提醒 → 后台常驻）。

## 2. 交付物

| 文件 | 作用 |
|---|---|
| `native/keepalive/src/main/java/com/siji/keepalive/SijiKeepAliveService.java` | 前台服务实现（约 200 行，单文件） |
| `native/keepalive/src/main/AndroidManifest.xml` | service 声明 + `foregroundServiceType=specialUse` + 三个权限 |
| `nativeplugins/siji-keepalive/package.json` | 本地原生插件描述（`integrateType: aar`，**无 UniModule**） |
| `nativeplugins/siji-keepalive/android/siji-keepalive.aar` | 构建产物（4 KB）：`classes.jar` + `AndroidManifest.xml` |
| `scripts/build-keepalive-aar.ps1` | 一条命令出 AAR（javac + jar + zip，不需要 Gradle / Android Studio） |
| `utils/keepalive.js` | JS 侧：开关、探测、启停、电池优化引导 |
| `pages/settings/sub/notify.vue` | 「后台运行」组（App 端） |

**为什么不用 `uni.requireNativePlugin`**：那需要 `uniapp-v8-release.aar`（DCloud 离线打包 SDK，几百 MB）来写 UniModule。本插件不需要任何 JS 桥 —— JS 侧用 `plus.android` 反射构造 Intent 就能拉起 Service，所以插件退化成「aar 里放一个 Service + manifest」，编译依赖只剩一份 `android.jar`。

## 3. 构建 AAR

```powershell
# JDK 8 / 17 / 20 都可以；脚本自己找 javac
$env:JAVA_HOME = 'C:\Program Files\Java\jdk-17'
& .\scripts\build-keepalive-aar.ps1 -AndroidJar 'C:\Users\c3798\AppData\Local\dsh-android\platform-34\android-34\android.jar'
```

实测输出（2026-10-19，jdk-17）：

```

[2/5] javac: C:\Program Files\Java\jdk-17\bin\javac.exe
```

**没有 Android SDK 时**（本机最初状态：只有 JDK，无 SDK / 无 Studio / 无 Gradle）——只需要一份 `android.jar`，不用装整个 SDK：

```powershell
$dir = "$env:LOCALAPPDATA\dsh-android"; New-Item -ItemType Directory -Force $dir | Out-Null
Invoke-WebRequest 'https://dl.google.com/android/repository/platform-34-ext7_r03.zip' -OutFile "$dir\platform-34.zip"
Expand-Archive "$dir\platform-34.zip" "$dir\platform-34"
# → $dir\platform-34\android-34\android.jar（约 63 MB 下载）
```

> 脚本里的 `pwsh` 说明：本机只有 Windows PowerShell 5.1（没有 `pwsh`），所以直接 `& .\scripts\build-keepalive-aar.ps1` 调用。**脚本必须存成 UTF-8 带 BOM**，否则 5.1 按 GBK 解码中文会把语法打断（本轮已踩：BOM 加回后正常）。

## 4. 打包装到手机

1. `manifest.json` 已注册插件（`app-plus.nativePlugins.siji-keepalive`）与权限（`FOREGROUND_SERVICE`、`FOREGROUND_SERVICE_SPECIAL_USE`）。
2. HBuilderX → 发行 → **制作自定义基座**（或云打包），在「App 原生插件配置」里勾选本地插件 `nativeplugins/siji-keepalive`。
3. 基座/APK 出来后装上，进「设置 → 提示与提醒」，「后台运行」组若显示开关可点 = 插件已进包；显示「当前安装包不支持」= 没进包（`utils/keepalive.js` 的 `isKeepAliveSupported` 探测的就是 `SijiKeepAliveService` 类加载）。

**尚未验证的一步**（必须实测，写在 `docs/真机验证清单.md` 2.23）：云打包/自定义基座是否接受 `package.json` 里 `plugins: []`（空数组，因为本插件没有 UniModule）。若被打包器拒绝，兜底两条：

- 兜底 A：改走离线打包 —— 把 `siji-keepalive.aar` 放工程 `libs/`，`AndroidManifest.xml` 里的 `<service>` 与三个权限手抄进宿主 manifest（Android Studio 工程，约 10 分钟）。
- 兜底 B：换插件市场现成的保活插件（零编译，但依赖第三方、质量与收费不可控）。

## 5. 运行时行为

```
App 启动（appReady）/ 回前台（onShow）
   → utils/keepalive.js syncKeepAlive()
       开关 siji_keepalive_enabled 关 → 确保不留残服务（stopService）
       开关开 + 类存在 → startForegroundService(Intent{class=SijiKeepAliveService, action=START})
                        → Service 起常驻通知（渠道 siji_keepalive，IMPORTANCE_LOW，不响不震）
                        → 点通知：getLaunchIntentForPackage(packageName) 回 App（不硬编码宿主 Activity）
   → 系统回收进程 → START_STICKY 由系统重启（intent 为 null 时用默认文案）
   → 用户划掉最近任务 → stopWithTask=false，服务不被一起停
```

**Android 版本分叉**（都在 `SijiKeepAliveService` 里判断）：

| SDK | 行为 |
|---|---|
| 21–25 | `startService` + `startForeground(id, n)`（通知渠道不存在，无需 channel） |
| 26–33 | `startForegroundService` + 渠道 + `startForeground(id, n)` |
| 34+ | 上面 + `startForeground(id, n, FOREGROUND_SERVICE_TYPE_SPECIAL_USE)`（不传类型会抛 `MissingForegroundServiceTypeException`） |

`startForeground` 抛异常（通知权限被拒/渠道被删）时服务直接 `stopSelf()`，**不会崩溃循环**。

## 6. 服务类型的取舍（为什么是 specialUse）

| 类型 | 结果 |
|---|---|
| `dataSync` | Android 15 起有 **6 小时/24 小时**运行上限，超时系统强停 —— 对「一直挂着」的场景等于自废 |
| `specialUse`（已采用） | 无时限；但需要在 manifest 写 `PROPERTY_SPECIAL_USE_FGS_SUBTYPE` 说明用途，**Google Play 审核要理由**，国内商店无此要求 |
| `shortService` | 只能跑 ~3 分钟，不适用 |

要改类型：`native/keepalive/src/main/AndroidManifest.xml` 的 `android:foregroundServiceType` + `SijiKeepAliveService.startAsForeground()` 里传给 `startForeground` 的常量，两处必须同时改，然后重跑构建脚本。

## 7. 排查

```powershell
adb shell dumpsys activity services com.HBuilder.UniApp   # 或实际包名；应有 SijiKeepAliveService, isForeground=true
adb logcat -s SijiKeepAlive:*                              # 服务自身日志极少，主要用于确认拉起
```

进程被杀后没重启：先看是否被 ROM 冻结（电池优化白名单 + 自启动），再看 `START_STICKY` 是否被 `stopSelf` 打断（通知权限被拒时会发生）。
