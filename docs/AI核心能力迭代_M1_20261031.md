## 2. 实现内容与设计差异

### 2.1 做了什么

1. **取数收敛**：`collectSnapshot` 逐字平移到 `context-pack.js`，`advice.js` 改为再导出。这是保证"Advice 兼容性"的唯一可靠做法——不重写、不优化、不顺手改口径。
2. **情境包**：`buildContextPacket({ now, deps, energyLevel })` 返回事实层 + 方向；`renderContextPacket(packet)` 渲染 ≤300 字，零数据返回空串。
3. **注入**：`buildChatMessages` 末尾追加，位置在全部既有注入之后、消息数组之前。

实际输出（实测样本）：

```
【当前情境】
计划：进行中 3 · 逾期 1（最久 6 天） · 今天到期 1
记录：近 7 天 1 篇
账单：本月 2 笔 ¥5700
方向：AI 工程 / RAG 方向；把想法做出来
```

### 2.2 与方案的差异（4 处，都有理由）

| # | 方案写的 | 实际做的 | 为什么 |
|---|---|---|---|
| 1 | packet 结果缓存 60s | **不缓存** | 纯 TTL 会让测试之间串数据（同一天同一时段读到的可能是上一个用例的库）。实测 300 个计划耗时 0.3~0.6ms/次，够用；要加缓存必须按数据指纹失效，那是 M2 的事 |
| 2 | 未提低能量处理 | **very_low 时隐去「计划」「人脉」两行** | 这两行是最典型的"你还差什么"盘点，低能量时看到就变成催促。与 4.5.1 跳过动静摘要同一口径 |
| 3 | 未提方向行 | 从画像 `职业方向/人生关键词/当前阶段` 取 ≤40 字，做成「方向：」一行 | 这是 M4 关联的锚点，M1 先把它放到离用户消息最近的位置 |
| 4 | 未提开关 | **不加能力开关** | 加开关要改 `features.js` 与设置页，`ai-features.test.js` 断言数量也要改；M1 无用户可见入口，回滚靠代码比加开关更干净 |

### 2.3 明确没做的事

**A3（无关旧记忆被注入，P7 的 3/3）不在 M1 修复。** 它属于 `selectMemories` 的"无命中回落最近 30 条"，与 `collectSnapshot` 无关；收紧它会直接影响"闲聊时也需要背景"的场景（4.5.1 已经为短 query 收窄过一次）。按你的授权，这条留在差距样本里，归入 **M4**，届时和关联触发一起做，并用同一批语料验证"该记的没被误过滤"。

### 2.4 验收对照

| 验收项 | 要求 | 结果 |
|---|---|---|
| 数据来源 | 复用现有取数，不改口径 | 通过（`collectSnapshot` 逐字平移，`advice.test.js` 30 条全过） |

| 长度 | ≤300 字 | 通过（40 个计划 + 超长方向仍 ≤300） |
| 记忆关联 | 不再无条件注入无关旧记忆 | **未做**（按你的授权归 M4，见 2.3） |

## 3. 测试结果

| 项 | 结果 |
|---|---|
| 全量 | **126 文件 / 1761 通过 + 1 expected fail（1762）**，29.25s（基线为 124 / 1745 + 1，27.85s） |
| 新增用例 | 16 条（context-pack 10 + baseline-probe 6） |
| advice 回归 | `tests/advice.test.js` 30 条全过，无改动 |
| 接入验证 | `buildChatMessages` 有数据时含情境段、当前库不含时无该段 |
| 体积 | 有数据样本 system 7044 字，情境包 93 字（1.3%） |
| 占比 | 关于用户的信息 390 → 483 字，5.6% → 6.9% |
| 性能 | 300 个计划 0.3~0.6ms/次（deps 注入，不含 storage 反序列化） |
| 禁用词 | 「应该/建议/需要/还没/加油/赶紧/尽快」零命中 |

测试里抓到的两件事（都已修）：
1. 第一版把「周末判定」自己写了一遍，与 `advice-context.isWeekend` 重复——改回 import，避免两份口径。
2. 第一版为了实现缓存留了个未定义变量，跑测直接 ReferenceError——顺带确认了"不做缓存"的决定。
