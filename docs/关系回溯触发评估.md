## 方法与口径

- **语料是合成的**：本轮没有真实对话日志，语料由我按 8 个类别构造（`utils/ai/eval/traceback-corpus.js`，22 例，每例自带数据前置）。**这不是真实用户语料**，结论只说明正则行为，不能替代真实使用观察。
- **确定性可复现**：不调模型、不联网，固定「现在」为 2026-10-19 15:00，同一份语料在任何机器上得到同一份正文。
- **两道门模型**（评估模型容易搞错的地方）：生产先过 `detectTracebackIntent`（是不是在问关系变化），再由 `buildTracebackContext` 的人物门（有没有提到已收录的人）。评估把 `contextBuilt`（人物门）与 `injected`（两道门都过 = 生产真实行为）分开记，否则会把「能构建」误判成「已注入」——本轮第一次跑就踩了这个坑，指标全错，修正后才得到上面的数。
- **人物匹配率只在「确实注入了」的用例上统计**：漏触发属于召回问题，不该摊到匹配率上（否则匹配率被漏触发拉低，看不出真实错误关联）。
- **`notContains` 断言不能用于上下文**：【表达规则】里那句「不许说『他变冷淡了』」本身就是反面例句，上下文含该字串是正常的。回复级安全只能交给真实模型语料（`utils/ai/eval/cases.js` 的 `relation-traceback-facts-not-verdicts`，`replyExcludes`）——本轮 `empty-history` 的安全断言因此从「不得出现该句」改成「必须说明没记录 + 必须给出禁令」。

## 缺口清单

> 缺口 2 / 3 已于 4.43.0 / 4.42.0 修复；缺口 1 仍开放（对应 3 条 `it.fails`）。

### ✅ 缺口 3：第三人关系错误归属 —— 已修复（4.42.0）

- 修前现象：「阿伟说他跟女朋友关系变差了」命中了意图，并注入**我和阿伟**的互动时间线——话题却是「阿伟与他人的关系」。
- 根因：人物门只判断「消息里有没有已收录的人名」，不判断「这段关系的主体和对象是谁」。
- 修法（`analyzeTracebackOwnership`，**不做关键词屏蔽，只识别主体/对象**）：
  1. **转述引语**：「X 说 / 告诉我 / 抱怨 …」后面描述的是 X 自己的关系 —— 引语里出现他者称谓（女朋友/家人/同事…）或「他/她 + 跟/和/与」即判第三人；
  2. **配对结构**：「X + 跟/和/与 + 他者称谓」—— X 是主体，对象不是用户；
  3. **名字落在别人的引语里**（「阿伟说他跟**小王**关系变差了」中的小王）—— 名字前面隔着「他/她/自己 + 跟/和/与」即判第三人；
  4. **用户优先**：引语主语或对象是用户（「阿伟说我最近和他疏远了」「阿伟说他最近和我不太联系」「阿伟跟我和好了」）一律按 self；
  5. **保守默认**：没有确凿第三人信号时按 self —— 宁可漏挡第三人，也不误挡用户自己的关系（误挡会让该触发时静默失效）。
- 效果：注入层误触发率 **11.1% → 0%**（0/14）；5 种第三人说法全部不注入；对照组（用户自己的关系 6/6、怀疑态度、空记录）不受影响。
- 边界：只跳过**回溯注入**，该消息的其他上下文（关系卡片、记忆、计划等）照常处理 —— 有测试锁定。

### 缺口 1：含蓄说法完全漏触发（4 例）

- 现象：「阿伟最近有点怪怪的」「感觉和阿伟不如以前了」「和小王聊天越来越没话说了」意图层不命中，回溯不加载。
- 根因：正则只覆盖显式词（疏远/冷淡/变差/不理我/不回我），没有「关系状态变化」这一类说法。
- 最小修法建议（**不扩关键词表**，加结构规则）：命中「已收录人名」+ 关系状态词（`不如以前|没以前|变了|怪怪的|不对劲|越来越没话说|生疏|客气`）即触发。风险由人物门兜底——实测证明人物门很硬（见结论 1）。

### ✅ 缺口 2：多人场景静默只选一人 —— 已修复（4.43.0）

- 修前现象：「为什么我和阿伟、小王都疏远了」只注入了小王（按「最近有互动」挑一个，静默丢掉另一个）。实测错配 5 例、人物匹配率跌到 61.5%。
- 根因：`buildTracebackContext` 用 `sort by last_interaction` 取 `[0]`，**选择依据与用户说的是谁无关**。
- 修法（`selectTracebackPersons`，只动候选筛选与组装逻辑）：
  1. **合格性**：必须落在含「关系变化」信号的**同一个分句**里 —— 顺带提及（「…，顺便说一句小王升职了」）不算；
  2. **归属**：复用缺口 3 的 `analyzeTracebackOwnership`，第三人关系的人跳过（「阿伟说他跟女朋友闹矛盾了，**小王**最近对我很冷淡」只回溯小王）；
  3. **顺序按消息中出现先后**（确定性，与 `last_interaction` / 存储顺序无关）；
  4. **上限 `MAX_TRACEBACK_PERSONS = 2`** —— 是注入上限，超出的人按上面的顺序**确定性丢弃**（不是「只看前两名就忽略其余」的隐式行为）；
  5. **每人一段**，段首标明对应人物，结尾共用一条表达规则并声明「各段分别对应谁，不要混在一起说」。
- 效果：多人场景静默取一 **4 例 → 0 例**；人物匹配准确率 **61.5% → 100%**（14/14）；召回 76.5% → **82.4%**（14/17）。
- 修复过程中又暴露两个组合缺陷，都是「归属判定必须与分句结构绑定」：① 转述引语的匹配**跨过了逗号**，把下一分句的「对我」当成上一句关系的对象 → 引语一律按分句截取；② 转述动词的回溯**跨过了逗号**，把上一分句的「他说…」算到下一分句的名字头上 → 分句边界加入逗号。

### 缺口 4：历史询问不注入（2 例）

- 现象：「上次我和阿伟聊得怎么样」不注入回溯。
- 判断：**不必修**。这类是事实查询，AI 走 `query_interaction` 更合适；回溯面向的是「关系变化分析」。已在语料里标为 `optional`。
- 4.43.0 起这类消息在评估里归入「两道门都未经过」（既没问关系变化，也没有合格人物），它连回溯上下文都不会构建。

## 结论

1. **人物门现在承担两件事**：① 归属（这段关系是不是用户的）② 合格性（这个人是不是落在关系变化句里）。所以放宽第一道门（意图）的误注入风险很低 —— 当前注入层误触发 **0/15**，且这一层不依赖关键词。
2. **下一步只剩缺口 1**：把含蓄说法纳入触发。做法是加结构规则而非扩词表（`不如以前|没以前|变了|怪怪的|不对劲|越来越没话说|生疏|客气` + 已收录人名）；改完 3 条 `it.fails` 应转正为普通断言。
3. 当前基线（34 例语料）：**召回 14/17（82.4%）· 误触发 0/15 · 人物匹配 14/14 · 安全性通过**。
4. 仍要强调：语料是合成的，这组数字**只适用于这组语料**；真实场景表现要靠上线后观察。缺口 3 保留的「保守默认 self」仍是明确的风险取舍 —— 部分间接转述会被判为 `self`。
