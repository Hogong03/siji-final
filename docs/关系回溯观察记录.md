# 关系回溯：真实使用观察记录

> 用途：触发规则已冻结（4.44.0），进入真实使用观察阶段。
> 本文件是**判定标准 + 处置流程**；**可直接填写的记录表在 `docs/关系回溯观察日志.md`**（含空白模板、合成示例、CSV 表头）。
> 真实记录请写到 `docs/关系回溯观察日志-本地.md`（已在 `.gitignore`，不会被提交）。
> 规则代码与离线评估见 `utils/relation-traceback.js`、`docs/关系回溯触发评估.md`。

## 一、观察窗口

- **建议时长**：1–2 周，或攒够 **30–50 个有代表性案例**。
- **这不是统计充分性保证**，只是便于执行的初始窗口；窗口结束后再决定是否继续观察或进入下一轮修复。
- 期间的硬要求：**只记录，不看到一例失败就改规则**。

## 二、记录原则（隐私）

- 只保存**必要且匿名化**的信息：把真实姓名换成「A/B/C」，删除可定位的细节（公司名、住址、电话）。
- 优先使用**等价改写的合成句**代替原话（例：「为什么我和张三最近疏远了」→「为什么我和 A 最近疏远了」）。
- **不要**为了评估无差别保存完整私人对话。
- 观察记录本身建议留在本地，不要提交进仓库（`docs/` 里只保留本模板；真实记录另存）。

## 三、判定标准（先在记录里标注「应该触发 / 不应该」）

**应该触发**（用户在说自己与某人的关系状态）：

| 类型 | 例子 |
|---|---|
| 明确关系变化 | 我感觉和阿伟最近疏远了 / 阿伟最近对我很冷淡 / 我和阿伟的关系是不是变差了 |
| 怀疑对方态度（点名） | 小王是不是讨厌我了 |
| 含蓄：双方状态变化 | 我和阿伟没以前那么亲近了 / 感觉和阿伟不如以前了 |
| 含蓄：双方交流变化 | 和小王聊天越来越没话说了 / 跟阿伟越来越没话说 |

**不应该触发**：

| 类型 | 例子 | 原因 |
|---|---|---|
| 纯状态描述（无双方指向） | 阿伟最近有点怪怪的 | 只描述状态，不构成"我与他的关系变化" |
| 转述他人关系 | 阿伟说他跟女朋友关系变差了 | 归属不是用户（缺口 3 已挡） |
| 泛化讨论 | 为什么有些人会越来越冷淡 | 没有人名指向 |
| 纯历史事实查询 | 上次我和阿伟聊得怎么样 | 走 `query_interaction`，不是回溯 |
| 没点名 | 他是不是不想理我了 | 没有人名，AI 应反问是谁 |

## 四、记录表

**可填写的表在 [`docs/关系回溯观察日志.md`](关系回溯观察日志.md)**（12 列含脱敏输入、空白行、3 条合成示例、CSV 表头、特殊情形记法）。本节只保留口径要点：

- **「是否应该触发」与「是否实际触发」必须分两列**：只有分开才能区分漏触发（应该=是、实际=否）与误触发（应该=否、实际=是）；合成一列只能统计"触发了多少次"，看不出对错。
- **不确定就写"不确定"**：没有人名的消息（「我感觉我们之间有点远了」）属于"没有明确回溯对象"，**不算漏触发**；观察重点是 AI 有没有自然反问"你说的是谁"。
- **历史查询不算未触发**：「上次我和 A 聊得怎么样」本来就该走 `query_interaction`。

字段口径：

- **实际触发**：提示词里到底有没有出现回溯段。若不方便看提示词，看回答里有没有引用用户自己的历史互动。
- **人物正确**：出现多个人名时，是否遗漏了用户明确提到的人 / 是否错认。
- **历史事实准确**：AI 说出的时间线（时间、场景、结果）与用户自己的记录是否一致。
- **事实/推测分开**：AI 有没有把"可能/猜测"直接说成"他就这样"。
- **回答有帮助**：这条用于判断功能价值，不用于判断规则对错。

## 五、四类问题分类与处置

| 分类 | 现象 | 归属模块 | 处置 |
|---|---|---|---|
| ① 意图漏识别 | 该触发的没触发 | `TRACEBACK_INTENT` | 攒够 ≥3 例同类表达，**先补语料再改规则** |
| ② 人物归属错误 | 注入了别人的回溯 / 只注入了其中一人 | 先分层定位（下表），再决定改哪里 | **安全类，出现 1 例即处理**（错误归属代价最高） |
| ③ 历史上下文构建错误 | 触发对但事实不对（漏条、错序、编造） | `getRelationTimeline` / 组装 | 先查数据本身是否缺失，再判断是否代码问题 |
| ④ 上下文正确但回答不佳 | 提示词没问题，AI 仍答得不好 | 提示词 / 模型，不是回溯规则 | 记录但不改回溯；必要时补 `utils/ai/eval/cases.js` 语料 |

**②类必须先定位问题层，确认是规则缺陷再改**（不能把所有问题都归因于触发规则）：

| 层 | 看什么 | 对应代码 |
|---|---|---|
| 意图门 | 这条消息该不该判定为"关系变化" | `detectTracebackIntent` |
| 人物筛选 | 是否漏选/错选（顺带提及被算进来？多人被丢？） | `selectTracebackPersons` |
| 归属判断 | 是否把"他跟别人"当成"我和他" | `analyzeTracebackOwnership` |
| 上下文组装 | 事实有没有串到别人名下 | `getRelationTimeline` / `buildPersonSection` |

**重新打开模块的门槛**：①③④ 类需 ≥3 例同类；②类 1 例即处理。任何改动前先补语料，改完跑下面两条命令。

## 六、离线回归网（观察期间保持常绿）

```powershell
# 端到端链路 + 触发范围评估（不需要模型、不联网）
npx vitest run tests/relation-traceback-e2e.test.js tests/relation-traceback-trigger.test.js
```

- `tests/relation-traceback-e2e.test.js`：验证「消息 → 意图 → 选人 → 归属 → 上下文 → **最终提示词**」整条链路（含关系图谱/记忆并存、`query_interaction` 兜底路径）。
- `tests/relation-traceback-trigger.test.js`：45 例语料的四项指标（召回 / 注入层误触发 / 人物匹配 / 行为安全）。

## 七、观察期结束后的决策

1. 若四类问题都未达门槛 → 保持规则冻结，功能进入正常维护。
2. 若 ② 类出现 → 优先修归属（可复用缺口 3 的结构化判定思路）。
3. 若 ① 类集中 → 按"结构组合"扩展（双方指向 + 变化线索），**不要加孤立关键词**。
4. 若 ④ 类集中 → 问题在提示词或模型侧，不在回溯规则；改提示词要同步补真实模型语料。
