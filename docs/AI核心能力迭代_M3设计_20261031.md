# M3 设计：从被动记录到「适时建议」

> 设计时间：2026-10-31
> 状态：**设计稿，未开工**。等你确认后进 M3.1。
> 前置：M1 情境包、M2 开放事项均已交付；本轮不碰 M4 记忆检索。

---

## 0. 一句话

M3 不是「多给几条建议」，是**给建议装上判断力**：什么时候说、说什么、什么时候不说。

判断力的最小实现是三件事：**候选必须带依据**、**同一时刻只出一条线**、**没有够格的候选就不弹**。

---

## 1. 多来源候选池（已批准）

| 来源 | 提供什么 | 在 M3 里的角色 |
|---|---|---|
| 现有 15 条规则 | 阈值信号（逾期/预算/断档/久未联系…） | **候选生成器**：保持现状，不改文案 |
| Open Loops | 用户真实说过、还没解决的事 | **候选生成器**（独立来源）：`open` 且悬了 ≥3 天才进池 |
| 用户画像 | 职业方向 / 人生关键词 / 当前阶段 | **镜头，不是生成器**：只用于给候选打分与过滤，不单独产出建议 |

> 为什么画像不生成建议：只凭"职业方向是 AI 工程"就推荐"你应该学 RAG"，正是你明确排除的「无依据的人生规划建议」。画像的正确用法是**判断这条建议是否顺着用户的方向**，以及**在两条候选之间选更贴的那条**。

---

## 2. 候选结构

```js
{
  id,            // 稳定标识：rule:plan-overdue / loop:<loopId> / goal:<field>
  source,        // 'rule' | 'loop'
  domain,        // plan | bill | diary | relation | profile | loop
  title,         // ≤12 字，能一眼做决定
  why,           // 一句依据，必须引用事实
  firstStep,     // ≤5 分钟可开始的一步；没有就为空，不编
  evidence: { ref, text },   // ref 必须能指回数据（计划 id / loop id / 计数）
  tone,          // urgent | nudge | info
  action,        // 复用现有 nav / prefill / guide
  score          // 内部排序用，不展示
}
```

**硬规则**：`evidence.ref` 为空或指不回真实数据的候选，**直接丢弃**，不进排序、不进面板。这是「有依据」唯一可执行的定义。

---

## 3. 五层过滤（从候选到面板）

```
原始候选（规则 N 条 + 循环 M 条）
  ↓ ① 依据校验：无 ref 的丢
  ↓ ② 去重：同域只留一条；loop 已挂 plan 的不重复；标题高相似（保守口径）只留一条
  ↓ ③ 冷却：同一 id 7 天内出现过 → 丢（siji_advice_seen）
  ↓ ④ 时机：能量/时段/让位规则
  ↓ ⑤ 节制：最多 3 条、最少 2 条；不足 2 条 → 不弹
面板
```

逐层口径：

| 层 | 规则 |
|---|---|
| ① 依据 | 规则类 ref = 计数字段名（如 `plans.overdue`）；循环类 ref = loop id；两者都可点开查看 |
| ② 去重 | 同 `domain` 只留 score 最高一条；`loop.plan_id` 非空则跳过该 loop；标题归一化后互相包含且多出部分是通用后缀时视为重复（沿用 M2 的口径） |
| ③ 冷却 | `siji_advice_seen = { id: lastShownAt }`；7 天内不再出现；用户点「不相关」→ 14 天 |
| ④ 时机 | 沿用 advice 现有门控（新的一天 / 签名变化 / 3 小时间隔 / 每天 2 次 / 4 条让位）；新增：`energy=low` 时最多 1 条且只保留非任务类；`very_low` 时不弹 |
| ⑤ 节制 | `MAX_DIRECTIONS=3`、`MIN_DIRECTIONS=2`；不足 2 条**返回空，不弹面板**——沉默是合法结果 |

---

## 4. 建议排序（判断力的核心）

`score = 紧急度 × 0.5 + 方向贴合 × 0.3 + 新鲜度 × 0.2`

- **紧急度**：urgent=1.0 / nudge=0.7 / info=0.3；逾期按天数封顶加分。
- **方向贴合**：候选文本与画像「职业方向 / 人生关键词」的字符重合度（0~1，纯本地，简单可解释）；无画像时统一 0.5，不惩罚。
- **新鲜度**：`loop.days` 越大越高（悬得久更值得提），上限 30 天；规则类用「距上次同类建议天数」。

排序只用于**选哪几条**和**谁排第一**，不展示分数，也不写成"重要度 87%"这种伪精确。

---

## 5. 反馈：接受 / 忽略 / 拒绝

| 动作 | 采集 | 用途 |
|---|---|---|
| 接受（点开或开始） | `accepted[id]++` | 提升同类候选权重 |
| 忽略（关面板不点） | `ignored[id]++` | 3 次后该 id 冷却 30 天 |
| 拒绝（点「不相关」） | `rejected[id]++` | 立即冷却 14 天 + 计入误报率 |

存储 `siji_advice_feedback`。三个数直接支撑验收指标，不需要额外埋点。

## 6. 与 M1 的重复清理

现状有两处重复（M1 报告已登记）：

1. 「进行中 N」同时出现在 `用户近期数据` 与情境包。
2. 「近 7 天记录数」与「近 3 月记录数」在语义上部分重叠。

M3 处理：
- 情境包**保留**逾期 / 今天到期 / 今日打卡（可行动）；
- 从情境包**删掉**「进行中 N」（它是背景，不是当下该做的事）；
- `用户近期数据` 不动（月度账本口径），避免两处都改导致数字对不上。

预计省 10~15 字，但更重要的是**减少模型看到两个口径的机会**。

## 7. 验收标准（可量化）

| 项 | 标准 | 验证 |
|---|---|---|
| 有依据率 | 面板里每条都能展开看到 ref 指向的数据 | 100%，单测 + 人工 |
| 方向多样性 | 同一次面板不出现两个同域方向 | 100%，单测 |
| 重复率 | 同一 id 7 天内重复出现 | 0，单测 |
| 沉默正确 | 有依据候选 <2 条时**不弹** | 100%，单测 |
| 误报率 | rejected ÷ shown | <20%（上线 2 周后看真实数据） |
| 低能量 | `low` 只给 1 条非任务项；`very_low` 不弹 | 单测 |
| 成本 | M3 主路径 0 次模型调用 | 请求体实测 |
| 回归 | 全量测试绿；Advice 现有 30 条不回归 | 全量 |

**"什么时候保持沉默"的度量**：统计「有候选但被 ⑤ 层拦下」的比例。这个比例过高说明规则太吵，过低说明太保守——上线两周后据此调阈值，不靠感觉。

## 9. 成本与风险

- 主路径 **0 次模型调用**：候选、排序、去重、时机全是本地纯函数。AI 收敛不进 M3 主路径（见第 10 节）。
- 上下文增量：面板本身不进 prompt；只有用户点了建议进入对话时，才走现有链路。
- 风险：① 规则偏吵（靠 ⑤ 层拦，需真实数据调）；② 画像方向词太少导致"方向贴合"恒为 0.5（退化为按紧急度排序，可接受）；③ 依据文案写得太像任务会破坏"不催"口径（文案要过一遍铁律 1/8）。

---

## 10. 需要你拍板的一件事

**AI 收敛要不要进 M3？**

- 之前定的是「规则出候选 + AI 收敛，每天最多 1 次」。
- 但 M2.5 的真实模型验证还没做，此时引入模型收敛，等于在**未验证的判断层上面再加一层不可测的判断**。

我的建议：**M3 先做纯规则版，AI 收敛排到 M3.5**，用两周真实的 rejected/shown 数据决定要不要上、以及收敛到什么程度。这样 M3 的验收不依赖 Key，也不会把"建议质量"和"模型发挥"混在一起。

如果你要按原计划在 M3 内做，我就加一个 `cfg` 开关默认关，等 M2.5 验证后打开——但那样 M3 的验收里会多一条"AI 收敛未验证"，和 M2 一样挂账。

## 11. 明确不做

- 自动建计划、自动改开放事项状态
- 大量主动推送 / 通知轰炸
- 无依据的人生规划建议（画像只做镜头）
- M4 记忆检索改造
- 独立的"建议中心"页面（仍用现有底部面板）
