# 关系回溯观察日志（可填写）

> **配套标准**：判定标准、问题四分类与处置流程见 `docs/关系回溯观察记录.md`；本文件只负责「记」。
>
> **隐私（重要）**：真实记录请写到**本地副本** `docs/关系回溯观察日志-本地.md`（该文件名已在 `.gitignore` 里，
> 不会被提交）。本文件只保留**空白模板 + 3 条明确标注为「示例」的合成案例**。
> 发布流程里有 `git add -A`，把真实私人对话写在本文件里会被一起提交。

## 一、填写说明

**时机**：每次对话结束后立刻记一行，不要攒到一天结束（细节会忘）。
**粒度**：一条用户消息 = 一行。同一句里有多个问题，只填最主要的那类问题，备注写清。
**姓名**：一律改成 `A / B / C`，并删掉可定位的细节（公司名、地名、电话）。

| 字段 | 怎么填 |
|---|---|
| 编号 | 自增序号（`1`、`2`……）；本地副本可与本文件编号不连续 |
| 日期 | `YYYY-MM-DD` |
| 案例类别 | 明确关系变化 / 含蓄表达 / 第三人关系 / 多人关系 / 无明确人物 / 历史查询 / 其他 |
| 脱敏输入 | 脱敏或等价改写后的一句话（例：「为什么我和 A 最近疏远了」） |
| **是否应该触发** | 是 / 否 / **不确定**（按标准判定；拿不准就写"不确定"，不要硬判） |
| **是否实际触发** | 是 / 否（看回答有没有引用你自己的历史互动；能看提示词就直接看回溯段） |
| 人物是否正确 | 是 / 否 / 不适用（没触发、或本来就没人名时填"不适用"） |
| 历史事实是否准确 | 是 / 否 / 无记录 / 不适用 |
| 事实与推测是否分开 | 是 / 否 / 不适用（AI 有没有把"可能/猜测"说成"他就这样"） |
| 回答是否有帮助 | 有帮助 / 部分有帮助 / 无帮助（判断功能价值，不用于判断规则对错） |
| 问题分类 | ① 意图漏识别 / ② 人物归属错误 / ③ 历史上下文构建错误 / ④ 上下文对但回答不佳 / 无问题 |
| 处理决定 | 继续观察 / 补测试 / 重开模块（默认先写「继续观察」） |

**为什么「是否应该触发」和「是否实际触发」必须分两列**：只有两列分开，才能区分**漏触发**（应该=是、实际=否）与**误触发**（应该=否、实际=是）。合成一列就只能统计"触发了多少次"，看不出对错。

## 三、三类特殊情形怎么记

### 1. 不确定的案例：不要强行判定

例：「我感觉我们之间有点远了」——里面**没有人名**，属于"没有明确回溯对象"。

- 填写方式：`是否应该触发 = 不确定`、`是否实际触发 = 否`、`人物是否正确 = 不适用`、`问题分类 = 无问题（无明确回溯对象）`。
- 观察重点不是"该不该触发"，而是：**AI 有没有自然地反问"你说的是谁"**。反问得好，就是正确行为。
- **不要把它算成漏触发**——没有人名就没有可回溯的对象，硬触发意味着系统替你猜一个人，那才是风险。

### 2. 归属错误：立即处理，但先定位问题层

出现一次错误人物回溯，就是高优先级（错误的历史会影响 AI 判断）。先保留脱敏案例，再逐层定位：

| 检查层 | 看什么 | 对应代码 |
|---|---|---|
| ① 意图门 | 这条消息到底该不该判定为"关系变化" | `detectTracebackIntent` |
| ② 人物筛选 | 是否漏选/错选了人（顺带提及被算进来？多人被丢？） | `selectTracebackPersons` |
| ③ 归属判断 | 是不是把"他跟别人"当成"我和他" | `analyzeTracebackOwnership` |
| ④ 上下文组装 | 事实有没有串到别人名下（时间线条目混了？） | `getRelationTimeline` / `buildPersonSection` |

**只有确认属于规则缺陷才改规则**，并在改之前先往 `utils/ai/eval/traceback-corpus.js` 补一条语料。

### 3. 历史查询：不算"未触发"

「上次我和 A 聊得怎么样」这类**事实查询**本来就不该走回溯，AI 应走 `query_interaction`。

- 填写方式：`案例类别 = 历史查询`、`是否应该触发 = 否`、`是否实际触发 = 否`、`问题分类 = 无问题`；在备注里记 AI 有没有正确调出互动记录。

## 四、观察期结束后的统计（按四类分别统计，不看单一综合准确率）

窗口建议 1–2 周或 30–50 例（**不是统计充分性保证**）。到期按下表汇总：

| 问题类别 | 计数 | 判定门槛 | 动作 |
|---|---|---|---|
| ① 意图漏识别 |  | ≥3 例同类表达 | 按「双方指向 + 变化线索」的结构方式扩展，**先补语料** |
| ② 人物归属错误 |  | **1 例即处理** | 按上面四层定位，确认为规则缺陷再改 |
| ③ 历史上下文构建错误 |  | ≥3 例 | 先查数据本身是否缺记录，再判断代码 |
| ④ 上下文对但回答不佳 |  | ≥3 例 | 改提示词或评估模型，**不要改触发规则** |
| 样本总量 |  | 建议 30–50 例 | 不足则继续观察 |

**观察期间保持规则冻结**：离线回归网常绿即可 ——

```powershell
npx vitest run tests/relation-traceback-e2e.test.js tests/relation-traceback-trigger.test.js
```
